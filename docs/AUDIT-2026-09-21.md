# Design-Engineering Audit — 2026-09-21

**Scope:** `@kala-ui/react` v0.1.0-beta.3 (`packages/react`, ~90 component
families) with a supporting pass over `packages/react-app`, build tooling, and
docs. **Question asked:** what makes these components hard to *customize*,
hard to *plugin* (build on, extend, wrap), and hard to *use*?

**Method:** three full-sweep audit passes (component API surface; theming
architecture; repo structure & DX) with file:line evidence, plus direct source
verification of the core customization machinery (`lib/slot-styles.ts`,
`config/*`, `styles/globals.css`, `theme-provider`, button/dialog/input/select).
Findings that could not be grounded in a file citation were dropped.

**Severity criteria**

| Tier | Meaning |
| --- | --- |
| **Critical** | Shipped-broken today, or a contract the library explicitly promises is violated in code, or deterministic breakage is scheduled (test timebomb). |
| **Major** | Blocks a legitimate customization / extension / adoption path at scale; consumers must fork, use `!important`, or accept inconsistency. |
| **Minor** | Hygiene, drift, inconsistency — annoying, occasionally costly, not blocking. |

---

## 1. Executive summary

The library has a genuinely good foundation: a documented token layer
(`globals.css` shape/density/motion knobs), a per-part override channel
(`slotStyles`), a per-family style-table convention (`src/config/<name>.ts`),
a `data-kala-component` marker contract, and ~3,400 passing tests. The
audits found **no missing markers, no swallowed refs (React 19 ref-as-prop
is used consistently), no untested component, and no missing barrel export**.

The problems are that the four good systems are each **incompletely rolled
out and unevenly honored**, and the layer that would let a consumer retheme
or extend at runtime **does not exist yet**:

1. **The customization contract is ~60% honored.** `slotStyles` is absent on
   8 families and partial on 4 more; one listed-“wired” component leaks the
   prop to the DOM. Only 30 of ~90 families have a `config/<name>.ts` table;
   `tag`, `banner`, `multi-select`, and `toast` keep large cva tables inline
   next to their config files (split-brain). The repo’s own downstream
   package (`react-app`) implements **zero** of the contract.
2. **Theming is compile-time only.** A closed 4-theme enum, no token/variant
   injection, no theme context consumed by components, per-instance-only
   `slotStyles`. A white-label consumer cannot register a brand; a consumer
   cannot add a Button variant without forking; two shipped example theme
   blocks (`.neutral`, `.accent`) are documented as selectable themes but
   rejected by the provider.
3. **The API surface drifts.** Three size scales, two error-prop
   vocabularies, two callback naming schemes (one component ships both),
   `variant+color` on four components but `color`-only on Banner, `asChild`
   on two components only, and a dead i18n prop trio on Button that leaks to
   the DOM as invalid attributes.
4. **Trust hazards:** one integration test reads a `.changeset/` file that
   `changeset version` deletes (CI breaks on the next release), and
   `avatar.ts` references `--color-online`/`--color-offline` tokens that are
   defined nowhere in the repo.
5. **Docs misdirect users.** THEMING.md advertises `neutral`/`accent`
   themes the provider rejects (M4), and root AGENTS.md points contributors
   to `docs/AUDIT-2026-08-27.md`, which does not exist anywhere in the repo
   (M17) — the docs the project tells you to trust cannot be trusted.

Counts at a glance: **3 Critical · 19 Major · 20 Minor** findings, each with
evidence below.

## 2. Architecture assessment — the current customization model

What a consumer can do today, and where each mechanism stops:

| Layer | Mechanism | Works | Stops at |
| --- | --- | --- | --- |
| Design tokens | `--kala-*` shape/density (8 knobs), motion, semantic colors in `globals.css`; 4 built-in themes + 2 example blocks | ✔ single-place retheming of radius/control-height/padding/duration for *compliant* components | Sizes hardcoded as `h-7/9/11` literals bypass the knobs (M2); no runtime token API (M1); example blocks not selectable (M4) |
| Class overrides | `className` (merged via `cn`), `style` | ✔ standard Tailwind merge | Loses to any `slotStyles.root` entry — surprising precedence (M8) |
| Per-part overrides | `slotStyles={{ root, <part> }}`; string → `cn` merge, object → `mergeStyle` | ✔ clean per-part channel where implemented | Missing/partial on 12+ families (C1); per-instance only, no global/config-level registration (M1, M8); non-variant-aware |
| Style tables | `src/config/<name>.ts` cva tables, re-exported from `config/index.ts` (machine-guarded completeness ✔) | ✔ lets consumers compose `buttonStyles` etc. | 30 of ~90 families; several families split between config and inline cva (M7) |
| Theme selection | `ThemeProvider` class-based switching, persistence, `color-scheme` sync, system tracking | ✔ solid implementation of a narrow feature | Closed enum, class-attribute only, no SSR script, no consumer themes (M1, M5) |
| Extension / plugin | Exported primitives + helpers (`applySlot`, `mergeStyle`, `SlotStyles`) “for downstream composite libraries” | ✔ types & helpers exported | `react-app` — the intended poster child — uses none of it (M16); internals of Toast/MultiSelect/Input unreachable (M11) |

**Verdict:** the model is *instance-tuned, compile-time theming*. There is no
path from here to (a) multi-brand runtime theming, (b) user-registered
variants, or (c) a downstream component library that *inherits* kala styling
conventions instead of copying them. Every gap below is a symptom of one of
those three missing paths.

## 3. Findings — Critical

### C1. The `slotStyles` “full-family” contract is violated in code
*Category: customize · Evidence: `.changeset/web-slot-styles.md:7`,
`src/__tests__/slot-styles-rollout.test.tsx:146`,
`ring-progress/ring-progress.tsx:78`, `stack.tsx:8-27`, `group/group.tsx`,
`overlay/overlay.tsx`, `spoiler/spoiler.tsx`,
`loading-overlay/loading-overlay.tsx`, `select/native-select.tsx`*

The shipped changeset promises “Full-family coverage: every component family
… accepts `slotStyles`”, and the rollout test’s `WIRED` list asserts it. In
code:

- **`RingProgress` is on the `WIRED` list but never destructures
  `slotStyles`** and spreads `{...props}` onto a plain `div`
  (`ring-progress.tsx:78`) — the prop leaks to the DOM as an unknown
  attribute. The test passes anyway: the family-level inventory check doesn’t
  verify per-part behavior.
- **Zero `slotStyles` support:** `Stack`, `Group`, `Overlay`, `RingProgress`,
  `Spoiler`, `LoadingOverlay`, `ErrorBoundary`/`ErrorFallback`,
  `NativeSelect` (while sibling `select.tsx` has 11 slot refs — a split-brain
  family).
- **Partial coverage, styled parts locked:** `Toast` (only `root`; the six
  per-toast surfaces at `toast.tsx:42-53` are hardcoded, several with
  `!important`), `Input` (only `root`; wrapper `input.tsx:91`, prefix `:93`,
  suffix `:111`, password toggle `:117` are literal-class), `Alert`
  (`root`/`icon`/`dismiss` only; `AlertTitle`/`AlertDescription` take no
  `slotStyles` at all), `Badge` (root only; loading arm hardcodes
  `h-5 w-16` at `badge.tsx:40`).

**Consumer impact:** the documented override channel silently no-ops on ~1 in
8 families and on half the parts of the busiest composites (toast, input).
Users fall back to `!important` against internal classes — the exact thing
the API exists to prevent.

### C2. Phantom tokens: `--color-online` / `--color-offline` are defined nowhere
*Category: customize · Evidence: `config/avatar.ts:27-81`;
`src/styles/` contains only `globals/helpers/theme/tokens.test`*

The avatar status-dot classes reference Tailwind v4 `--color-*` variables that
no theme block defines. The status colors render as no-fill today, and cannot
be themed by design because they aren’t tokens in the token system. This is
also the proof of a missing guard: no test asserts “every class in a config
table references a defined token/class” (see M3).

### C3. Integration test reads a transient release artifact — CI timebomb
*Category: use/DX · Evidence:
`src/__tests__/slot-styles-config.integration.test.ts:13-33`*

The machine-guard for config-table completeness does
`readFileSync("../../.changeset/web-slot-styles.md")` and asserts its text.
`changeset version` **deletes consumed changeset files** — the next release
makes this test throw ENOENT and breaks `pnpm test` for everyone. A test must
assert the *contract*, not quote a release note.

## 4. Findings — Major

### Theming & customization

**M1. No runtime theme or config API (root architectural gap).**
Closed 4-value `THEMES` enum (`theme-provider.tsx:20-25`); no token or
variant injection; components read no theme context; `slotStyles` is
per-instance only and not variant-aware (`lib/slot-styles.ts`). Consequences:
a new Button variant or brand palette requires wrapper forks per component;
there is no `KalaProvider`-level `defaultSlotStyles`/`tokens`/`variants`
registration. *This is the single highest-leverage gap — most other
customization findings are its symptoms.*

**M2. Density/shape knobs cover 8 values; sizes/radii hardcoded everywhere
else.** `h-7/9/11`, `px-2/3/8`, `rounded-md/lg` literals bypass
`--kala-control-h/px`, `--kala-radius-*` in `config/button.ts:33-36`,
`config/alert.ts:6,152`, `config/dialog.ts:13-16`,
`config/dropdown-menu.ts:3`, `config/number-input.ts:3`,
`config/avatar.ts:5-9`; worst, `select.tsx:74-75` keeps `h-9`/`h-10` inline
in the component — not even in its own config table. A consumer who sets
`--kala-control-h` gets inconsistent control heights across the library.

**M3. Token layer has no parity guard and duplicated formulas.** Nothing
asserts each of the seven theme blocks defines the required token set — a
missing token in `.dark` ships silently (`tokens.test.ts` pins 4 components’
radius strings only). The `border-alpha` color-mix formula is hand-copied in
3–4 places (`theme.css:46-50`, `globals.css:283-287`, `helpers.css:44-48`,
card variant `helpers.css:28-33`, which also re-derives `--shadow-themed`
from `theme.css:204-209`). Tailwind-mode consumers must **copy-paste** the
`:root`/`.dark` blocks (THEMING.md:222-224) with no `tokens.css`-style import
to alias — copied defaults drift on every upgrade.

**M4. Docs advertise themes the provider rejects.** THEMING.md:53-55 and
:115-117 list `neutral`, `accent`, `dark accent` as themes; the provider
enum rejects them and `themes.cross-platform.integration.test.ts:70-77`
asserts they are absent. Following the doc produces invalid theme names.

**M5. Class-only theming; no SSR story.** The precompiled dark variant keys
off `.dark` only — `[data-theme="dark"]` is unsupported; there is no
no-FOUC inline script for SSR apps (theme applied post-hydration via effect,
`theme-provider.tsx:124-135`), so server-rendered apps flash.

**M6. `Overlay` bypasses the `--overlay` token it is named after.** Defaults
to literal `#000` + a local `hexToRgb` (`overlay.tsx:25-39`); named/oklch
colors silently drop `backgroundOpacity` (acknowledged in comments at
`:58-71`). TOKEN_SPEC.md:43 ships `--overlay`/`--overlay-alpha` that this —
the only overlay consumer — never reads.

### Style-source discipline

**M7. Config-table convention honored by 30 of ~90 families; split-brains
where both exist.** `packages/react/AGENTS.md:25` states config tables are
the style home with “no literal Tailwind base strings” in `.tsx`; in reality
`collapsible.tsx:48`, `indicator.tsx:7-44`, `spinner.tsx:8-28`,
`overlay.tsx:77`, `field.tsx:90`, `label.tsx:10-12`, all of `loading/*`
keep base strings inline, and `calendar` is on the rollout `WIRED` list with
no `config/calendar.ts` at all. Split-brains: `tag.tsx:11-148` (full cva
inline; `config/tag.ts` holds only icon/remove), `banner.tsx:21-41` (same
pattern), `toast.tsx:42-53` (~500 chars hardcoded, `!important`-laden),
`multi-select.tsx:273-431` (20 literal class sites: chips, clear button,
group headers), plus a component-local `selectTriggerVariants` cva exported
from `select.tsx:52-55` beside `config/select.ts`. Consumers cannot reuse
what isn’t in config.

**M8. `slotStyles` precedence and reach have sharp edges.** Any
`slotStyles.root` entry beats the consumer’s own `className` (documented but
inverted from Tailwind intuition — the *later* prop loses); the object
channel via `mergeStyle` bypasses utility cascade entirely, so
`{ root: { color: "red" } }` cannot be overridden by any class; slots are not
variant-aware (no `slotStyles.sizes.lg`); there is no context-level default
(see M1). Evidence: `lib/slot-styles.ts:14,42,50-57`; dialog docs at
`dialog.tsx:91`.

### API consistency (ease of use)

**M9. Variant, palette, and size vocabularies drift per component.**
- `variant` + `color` on Button/Tag/Badge/Alert, but **Banner is
  `color`-only with a reduced palette** (info/warning/destructive/success —
  no primary/secondary/muted, no fill-style axis) (`banner.tsx:25-30` vs
  `config/alert.ts:7-21`).
- Size scales disagree: Button `xs/sm/md/lg/icon` (`config/button.ts:31-37`),
  SelectTrigger `sm/md`, Avatar `xs/sm/md/lg/xl`, RadioGroup `sm/md/lg`,
  Tag `sm/md/lg`. **Badge has no size prop at all** (`config/badge.ts:7-26`).
- Shape: Badge exposes `shape: rounded|pill`; **Tag hardcodes `rounded-full`**
  (`tag.tsx:12`).
- Error-state vocabulary: Input `hasError`/`hasSuccess` (`input.tsx:30-31`)
  vs RadioGroup boolean `error` variant (`config/radio-group.ts:30-32`).
- Spelling: Alert `dismissable` (`alert.tsx:41`) vs conventional
  `dismissible`.
- Dual value props: `DateRangePicker` accepts both `value` and `dateRange`
  (`date-picker.tsx:134` area).

**M10. Callback naming: two schemes, one component ships both.** The
convention is `onValueChange` (combobox, date-picker, multi-select, rating,
segmented-control, steps, tag-input, time-picker, color-input, file-upload).
Outliers: **number-input** redefines DOM `onChange` with a semantic payload
`(value: number | undefined)` (`number-input.types.ts:14`,
`number-input.tsx:218`) — colliding with native typing for an `<input>`;
**tag-input defines both** `onValueChange` (`tag-input.tsx:25`) and legacy
`onChange?: (tags: string[])` (`tag-input.types.ts:12`); Input/Textarea/
NativeSelect use DOM `onChange` (correct, but a third shape to juggle).

**M11. Internal-only parts and injected defaults block extension.**
- **Toast exports only the `Toaster` wrapper** (`toast.tsx:60`); per-toast
  markup is unreachable.
- **MultiSelect** renders chips, clear button, group headers, checkbox rows
  inline (`multi-select.tsx:273-431`) — no exported parts, no slot addresses;
  restyling means fighting `!important`.
- **Input**’s password-toggle button and prefix/suffix wrappers are
  internal-only (`input.tsx:93-133`); additionally, `unstyled` silently
  drops `prefixIcon`/`suffixIcon` (the bare-input branch at `input.tsx:76-87`
  ignores them) and the toggle’s aria-labels (`"Show password"`/`"Hide
  password"`, `input.tsx:118`) are not overridable.
- **Auto-injected, fixed glyphs:** Alert’s color→icon map (`alert.tsx:25-33,
  134-140`), Alert/Banner/Tag dismiss `X` at fixed sizes (`alert.tsx:151`,
  `banner.tsx:13,130`, `tag.tsx:4`), Dialog’s close `X` + hardcoded English
  `sr-only` “Close” (`dialog.tsx:123-130`), non-overridable aria-labels
  (`"Close banner"` `banner.tsx:128`, `"Dismiss alert"` `alert.tsx:149`).
- **Button’s i18n prop trio is dead and leaks:** `translationKey`,
  `loadingTextKey`, `disabledTextKey` (`button.types.ts:13-17`) are never
  read in `button.tsx` and fall through `{...props}` onto the DOM node as
  invalid attributes.
- **`TooltipContent` auto-injects the Arrow after `children`**
  (`tooltip.tsx:69-74`), breaking Radix `asChild`; **`DialogContent` forces
  its own `DialogPortal`** (`dialog.tsx:104-110`) with no prop passthrough,
  so Radix’s `container` option is unreachable.

**M12. `asChild` asymmetry.** `Button` (`button.tsx:30`) and `Badge`
(`badge.tsx:23`) support it; `Alert`, `Banner`, `Tag`, `Input` do not — no
stated rule for which components are polymorphic.

### Structure, tests, docs, build

**M13. Marker integrity: right attribute, sometimes wrong element or wrong
value, weakly guarded.** All families carry `data-kala-component` ✔, but the
marker lands on **Portal wrappers instead of the styled Content** in
`dropdown-menu.tsx:59`, `tooltip.tsx:62`, `select.tsx:176`, and
`dialog.tsx:106`; stuttered values like `"date-picker-date-range-picker"`
(`date-picker.tsx:183,201`) and `"card-with-image-card-skeleton"`
(`card-skeleton.tsx:126,158,200,241,290,310`); the guard test pins only
Button/Card/Input/Paper (`__tests__/component-markers.test.tsx`) — 4 of ~90.

**M14. 71 of 96 component dirs have no `<name>.types.ts`** (24 ship one:
alert…time-picker). Badge, Tag, Banner, Tooltip, Drawer, DropdownMenu,
Dialog, and 63 more inline their props. The convention (and the good
`ButtonProps extends Omit<React.ComponentProps<"button">, "color">` pattern)
is the exception, not the rule.

**M15. Overlapping/ambiguous families, undocumented boundaries.**
`Collapse` (framer-motion) vs `Collapsible` (Radix) vs `Spoiler` — three
collapse-alikes, no guidance; `collapse` additionally has no stories.
`loading/` has no `loading.tsx` (dir exports PageLoader/SectionLoader).
`Tag` vs `Badge` vs `Indicator`, `InputGroup` vs `Field` vs `Label`
(`FieldLabel` vs `Label` is a real trap), `Paper` vs `Card` — distinct but
unexplained; react-app ships `social-login-button/` **and**
`social-login-buttons/` as two near-duplicate dirs.

**M16. `react-app` implements none of the customization contract.** Zero
`slotStyles` matches in the whole package; no `src/config/` at all (all
inline Tailwind, e.g. `app-shell.tsx:44-51,122-126`); DataTable (691-line
`data-table.tsx`) has no per-column theming beyond `className`. The core
exports its helpers “for downstream composite libraries” — the first-party
downstream doesn’t use them, which is both a gap and the proof the plugin
story doesn’t survive contact.

**M17. Documentation drifts from code in ways that misdirect users.**
- CONTRIBUTING.md “Adding Components” teaches `__tests__/` layout
  (`:243`) when 94/96 dirs colocate tests; its file tree omits
  `<name>.types.ts` that its own step 2 imports; it never mentions the
  config table, marker, `"use client"`, or `slotStyles` hard rules
  (AGENTS.md:25-32) — and AGENTS.md is LLM-only by its own header, so human
  contributors have no accurate guide.
- THEMING.md theme list wrong (M4).
- Root AGENTS.md directs readers to `docs/AUDIT-2026-08-27.md`, which does
  not exist anywhere in the repo (verified by filename search).
- TOKEN_SPEC.md omits the motion (`--kala-duration-*`, `--kala-ease`) and
  typography (`--font-heading`) tokens THEMING.md documents — the two
  contract docs cover different surfaces.
- Stale counts everywhere (“~90 web components” vs “~85” vs actual 95–96
  dirs; “3,600+ tests” vs “~3,400”).

**M18. Build & packaging fragility.** POSIX-only `cp` in the build script
(`packages/react/package.json:416`) breaks Windows; hand-enumerated ~90-entry
`exports` map with no wildcard and visible ordering drift (`:214-221`,
`:398-413`) — every component is a 3-place manual chore; `design-system/`
(Storybook-only internals) is compiled into the published `dist` because
`tsconfig.json` includes all of `src`.

**M19. Two components are unreachable in Storybook** (`collapse`,
`theme-provider` — no stories files).

## 6. Gap taxonomy — customize / plugin / use

| Concern | Blocking findings | One-line diagnosis |
| --- | --- | --- |
| **Customize** (retheme, restyle, rebrand) | M1, M2, M3, M4, M6, C1, C2, M7, m2, m4 | Tokens exist but coverage is partial and compile-time; the override channel is unevenly implemented; nothing is runtime-injectable. |
| **Plugin** (extend, wrap, compose, downstream kits) | M1, M11, M12, M16, C1, M13 | Exported style tables + slot helpers are a real plugin surface — honored by ⅓ of the library and bypassed by the library’s own app package; internals of the richest composites are unreachable; markers (the query contract) are misplaced on portals. |
| **Use** (adopt, discover, integrate) | M9, M10, M14, M15, M17, C3, M5, M18, M19 | Every cross-component decision (size, palette, callback, i18n, theming mode) must be re-learned per component; the human onboarding doc teaches a layout the repo doesn’t use; the next release breaks CI. |

## 7. Remediation roadmap

Ordered by severity and dependency — token/config unification precedes
variant/API work; runtime theming builds on both. The repo is pre-1.0
(`0.1.0-beta.3`) and per project rules carries no backward-compatibility
obligation: prefer clean rewrites over patches at every step.

**Phase 0 — stop the bleeding (days)**
1. Replace the changeset-reading assertions in
   `slot-styles-config.integration.test.ts` with a contract check against
   `config/index.ts` (C3).
2. Fix `RingProgress` slot leak; move markers off Portal elements onto
   Content (`dropdown-menu`, `tooltip`, `select`, `dialog`); de-stutter
   marker values; widen the marker test to every family (C1 partial, M13).
3. Add `--kala-status-online`/`--kala-status-offline` (or
   `--color-online/offline`) tokens to all six theme blocks and add a
   token-parity test plus a “every config class resolves” lint (C2, M3).
4. Delete Button’s dead `*TextKey` props (M11) — no compat needed.

**Phase 1 — make the existing model true (weeks)**
5. Complete `slotStyles` on the 8 missing families and the partial 4; add
   per-part rollout assertions so `WIRED` means wired (C1).
6. Migrate every family to `config/<name>.ts`; kill the split-brains
   (`tag`, `banner`, `toast`, `multi-select`, `select` trigger, `calendar`)
   — DONE: all six source every base/variant string from their config
   tables (incl. new `multi-select.ts`/`calendar.ts`), the exported cva
   doubles are deleted, and the select trigger's rendered truth (w-full,
   rounded-md, --kala-control-h) moved into its table. Still open: make
   literal base strings in `.tsx` a lint error (M7) and migrate the
   long-tail families (collapsible, indicator, spinner, overlay, field,
   label, loading/*).
7. Replace size/radius literals with `--kala-*` utilities across
   button/alert/dialog/dropdown/number-input/avatar/select; extend the knob
   set only if a need survives that pass (M2).
