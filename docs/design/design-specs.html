Foundation design specs

The design standard underneath every kala-ui component, web and React Native. This file is the dependency root: components.html (standard components + states) and app-components.html (app-level composites) are built exclusively from the tokens and rules defined here — no component may introduce a color, radius, duration, or size that this file does not declare.

Values are transcribed from the working web implementation — packages/react/src/styles/globals.css and packages/react/TOKEN_SPEC.md — so what ships in code today and what is specified here cannot drift silently. React Native mapping per docs/RELEASING.md-adjacent decision record docs/REACT-NATIVE-STRATEGY.md.

How to read this file Every swatch, button, and card on this page is rendered with the tokens themselves — the document is a live consumer of the system it specifies. The tables inside Light / Dark panels use fixed scopes (always accurate); the page chrome follows the toggle in the header.

1 · Visual identity §

What makes a kala-ui surface recognizable — the rules a component author applies before reaching for any token.

Shape voice: crisp

Controls at 6px, cards at 8px (via --kala-radius-control / --kala-radius-card). Small pill radii are reserved for semantic elements only — badges, switches, tags — and are deliberately not tokenized; pill-everywhere is a look kala rejects.

Depth: flat, hairlines carry structure

Default elevation is --shadow-alpha: 0 — flat. Separation comes from 1px hairlines (--border, --separator), tinted surface steps (--background → --muted → --card), and ink. Shadows appear only where platform convention demands lift: popovers, dropdowns, dialogs (--shadow-alpha > 0 per theme). No card-in-card; grouped records are one wrapper surface with hairline dividers.

Color character

One saturated ink-blue action color (--primary), a slate-tinted neutral ramp (borders and muted text sit at hue ≈ 211–221, never pure gray), and semantic hues biased to read as one family. One primary action per screen — secondary placements become quiet text or outline treatments.

Density

Compact, tool-like: 40px default controls (--kala-control-h), 24px card padding. Touch contexts scale up via the native adaptation rules in §8, never down.

2.2 · Contrast contract kala-ui pairs every fill with a *-foreground. The consuming app owns AA contrast between each pair: body text ≥ 4.5:1, large text/UI ≥ 3:1, in both themes. Saturated fills take a dark foreground where that clears the bar — see dark --primary-foreground and --warning-foreground. A rebranded theme that ships only fills, without re-checked foregrounds, is broken by definition.

6.1 · Containment rules

  • One containing box between the page/screen and any content block. Grouped records = one wrapper surface with hairline dividers — never a card per record, never card-in-card.
  • Horizontal scrollers bleed: chip/filter rails and carousels span edge-to-edge; the page gutter becomes the rail's internal scroll-content padding, so the first item aligns at rest and the last can arrive. Padding the items instead is a bug.
  • One primary action per screen. Secondary placements are quiet text or outline treatments.
  • Native screens own a 16px screen gutter (space-4); headers and tab bars bleed edge-to-edge; all screens respect safe-area insets (§8).

7.1 · Native spring tokens (Reanimated)

TokenConfigApplies to

Bans: no bounce on informative transitions, no pulsing status dots, no elastic easing, no auto-scroll. Motion explains state change — it is never decoration. Users with prefers-reduced-motion / iOS Reduce Motion get instant state swaps (duration 0).

  • Interactive elements: accessibilityRole + label always; state announced (accessibilityState).
  • Minimum target 44×44pt including invisible hit-area padding.
  • testID convention k-<component>-<part> (k-button-root, k-sheet-overlay) — contractual, mirrors the web marker classes.

9 · Customization model §

How an app adapts the standard without forking components. The ladder is ordered — every tier must exist, none may be skipped past.

Tier 1theme override
App registers a theme that overrides token values (colors, radii, spacing, motion). paisa trak gets its green; roadpulse its high-contrast. One registration rebrands everything. Web: :root custom properties. Native: a named Unistyles theme.
Tier 2variant props
Per-usage intent through the component API: variant, size, tone. The variant matrix is specified per component in components.html — components ship no styling props outside it.
Tier 3slot styles
Surgical escape hatch: a styles object keyed by part — styles="{ root: …, label: … }" — the native equivalent of Radix per-part className. Rule: if an app reaches for slots twice for the same need, that need becomes a variant in the library.
9.1 · Web override surface Import @kala-ui/react/styles once or define :root yourself and skip it; provide a dark block (kala expects both); flip themes by toggling the class/attribute on <html>. That is the whole surface — no !important, no re-vendoring.
9.2 · Governance Changing a token value here = a kala-ui release + changeset. Changing a token name = a breaking change with a migration doc (see docs/MIGRATION-0.1.md pattern). Components referencing values not in this file fail spec review. The two downstream spec files (components.html, app-components.html) may only reference tokens defined above.
